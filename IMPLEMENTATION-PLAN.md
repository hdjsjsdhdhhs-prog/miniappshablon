# IMPLEMENTATION-PLAN.md 

## Универсальный Telegram Mini App для витрин магазинов 


## 1. Цель и продуктовая модель 

Создать полноценный Telegram Mini App для вейп-шопов, который можно быстро переоформлять и повторно использовать для разных магазинов. В первой версии должны работать витрина, каталог, категории, карточки товаров, выбор вкусов и цветов у добавленных товаров, корзина, профиль покупателя и отдельная веб-админка. 

Цель — за несколько минут подготовить новую витрину для другого магазина: указать название, загрузить аватарку/логотип и фотографии, выбрать цветовую палитру, создать категории, внести товары, цены, вкусы, цвета и остатки. При этом не требуется менять исходный код, плодить репозитории или собирать отдельный frontend для каждого магазина. 

### Основной инвариант 

**Один репозиторий, один frontend-билд, один проект Supabase, много независимых магазинов.** Для каждого магазина хранятся отдельные настройки, каталог, остатки, заказы и членства владельцев. Добавление нового магазина не должно ломать или переодевать ранее созданные магазины. 

### Границы первой версии 

- Это каталог и оформление заказа, а не полноценная ERP-система. 
- Онлайн-эквайринг и криптоплатежи не подключать. Первый релиз создаёт заказ, а магазин подтверждает его и согласовывает способ оплаты/получения вне Mini App. 
- Не добавлять AI-помощника, push-уведомления, PWA или сложную лояльность без нового подтверждённого требования. 
- Приложение проектируется прежде всего для Telegram Mini Apps. 
- Профиль покупателя и доступ к его заказам должны работать на основании проверенной Telegram-идентичности, а не фиктивной регистрации. 


## 2. Стек и решения 

Использовать следующий стек, если аудит не выявит конкретную несовместимость: 

### Frontend 

- TypeScript в `strict`-режиме. 
- React. 
- Vite. 
- React Router. 
- pnpm и lockfile. 
- `@tma.js/sdk-react` для Telegram Mini Apps. 
- Tailwind CSS v4. 
- shadcn/ui. 
- Phosphor Icons. 
- TanStack Query v5. 
- React Hook Form и Zod. 
- CSS Variables для runtime-тем каждого магазина. 

### Supabase/backend 

- Supabase PostgreSQL. 
- Supabase Auth для владельцев. 
- Supabase Storage для логотипов и фотографий. 
- Row Level Security (RLS). 
- Supabase Edge Functions для серверных операций, которые требуют проверки Telegram `initData`, атомарного оформления заказа или повышенных полномочий. 
- SQL migrations в `supabase/migrations/` как воспроизводимый источник схемы. 
- Supabase CLI для локальной разработки, миграций, функций и seed. 

Публичное чтение опубликованного каталога может выполняться через Supabase client с корректными RLS-политиками. Операции заказа и чтение приватных заказов покупателя выполняются через серверную функцию с проверкой исходного Telegram `initData`. Владелец может работать через Supabase Auth и строго ограниченные RLS-политики либо серверные функции; выбор должен оставаться единообразным и задокументированным. 

### Качество и доставка 

- Vitest. 
- React Testing Library. 
- Playwright. 
- ESLint. 
- TypeScript strict. 
- GitHub Actions. 
- Vercel для публикации frontend. 
- Supabase MCP и Vercel MCP, если они доступны и авторизованы; официальные CLI — резервный вариант. 

### Обработка изображений 

Использовать `browser-image-compression` или совместимую поддерживаемую библиотеку для проверки и сжатия изображений на клиенте до загрузки. Для подходящих изображений использовать WebP. Размеры, качество и лимит загрузки должны быть централизованными настройками, а не разбросанными по компонентам. 

### Не добавлять без необходимости 

Не добавлять OpenAI SDK, дату/таймзоны, `vite-plugin-pwa`, Workbox или `liquid-gl` в базовый стек. Telegram Mini App не требует обязательной PWA-архитектуры. Сложные графические эффекты могут замедлить WebView и не являются функциональной необходимостью. Дополнительная библиотека допустима только при наличии конкретной задачи, проверки совместимости и записи решения. 

## 3. Важное ограничение тарифов 

Не переключать тарифы, не добавлять платные сервисы и не подтверждать платные действия без отдельного согласия пользователя. MCP/CLI должен показать реальное состояние аккаунта и проекта; не выдумывать, что публикация возможна бесплатно, если условия говорят обратное. 

## 4. Skills, design system и MCP 

До написания страниц: 

1. Изучить существующий репозиторий, `AGENTS.md`, инструкции установленных skills, `package.json`, lockfile и Git status. 
2. Найти доступный skill `ui-ux-pro-max` и применить его рекомендации к планированию мобильного каталога и административной панели. 
3. Если установлен Astryx Design System, прочитать инструкции его init и реально установленную документацию. Исследовать команды `build`, `template`, `component`, `docs layout`, `docs tokens` — только если они существуют в установленной версии. 
4. Перед использованием незнакомого Astryx-компонента изучить документированный API и доступные props. Использовать официальный CSS и документированный Theme provider. Не смешивать несовместимые версии shadcn/Drawer API. 
5. Проверить дизайн-токены, CSS layers и совместимость Astryx с Tailwind/shadcn. Если Astryx отсутствует или несовместим, использовать Tailwind v4 + shadcn/ui и зафиксировать причину. 
6. Проверить MCP Supabase, Vercel и браузерный MCP. Использовать доступные инструменты для исследования документации, правильного проекта, схемы, диагностики деплоя и проверки ссылок. 
7. Все изменения Supabase оформить и сохранить в SQL migrations. MCP может применяться для работы с проектом, но операции должны быть воспроизводимы из репозитория. До деструктивных операций запросить подтверждение. 


## 5. Архитектура tenants и маршрутов 

### Маршруты публичной витрины 

- `/s/:slug/` — главная и основные подборки. 
- `/s/:slug/catalog` — каталог и фильтры. 
- `/s/:slug/product/:productId` — карточка товара. 
- `/s/:slug/cart` — корзина и создание заказа. 
- `/s/:slug/profile` — профиль покупателя и его заказы. 

### Маршруты админки 

- `/admin` — вход владельца. 
- `/admin/shops` — список магазинов, доступных текущему пользователю/администратору платформы. 
- `/admin/shops/:slug` — панель магазина. 
- `/admin/shops/:slug/products` — товары и варианты. 
- `/admin/shops/:slug/categories` — категории. 
- `/admin/shops/:slug/orders` — заказы. 
- `/admin/shops/:slug/settings` — оформление и параметры магазина. 

Допустима небольшая перестройка маршрутов, если не теряется перечисленная функциональность и ссылки корректно открываются напрямую. Vite SPA на Vercel должна иметь правильный fallback/rewrite для глубоких ссылок. 

### Определение магазина 

По slug загружается опубликованная конфигурация магазина. Наличие slug в URL не предоставляет права владения. При запросе приватных данных полномочия определяются по проверенной личности и членству в `shop_memberships`. 

Все query keys TanStack Query, относящиеся к магазину, обязаны включать `shop_id` или уникальный slug. При смене магазина не должны переиспользоваться предыдущие данные. Корзины разных магазинов должны быть независимыми. 


## 6. Конфигурация нового магазина 

Каждый исходный tenant имеет структуру: 

`tenants/<slug>/shop.config.json` 

и директорию локальных исходных изображений, например `tenants/<slug>/assets/`. 

Конфиг должен содержать публичные начальные значения: 

- `slug`; 
- `name`; 
- `description`; 
- `logo`; 
- `theme`; 
- `currency`; 
- `initialCategories`; 
- `shopInformation`; 
- публичные Telegram-настройки/параметры запуска; 
- `ageRestriction`; 
- `legalNotice`; 
- начальные продукты/варианты — только если это нужно для repeatable seed. 

Не помещать в конфиг реальные ключи Supabase, `service_role`, пароли владельцев, токены Telegram-бота или любые серверные секреты. 

**Разделение источника истины:** `shop.config.json` — источник начальных данных и вход конвейера. После создания магазина Supabase является runtime-источником каталога и настроек. Изменения владельца из админки записываются в БД и не должны перезаписываться повторным импортом конфигурации. Re-seed должен быть идемпотентным и не должен обнулять пользовательские изменения. 

Новый tenant изначально создаётся в preview/unpublished-состоянии. Перевод в live — отдельная операция после проверки. 

## 7. Внешний интерфейс и UX 

### Общий визуальный язык 

Начальная тема — Dark Premium: почти чёрный/графитовый фон, светлый текст, контрастные нейтральные карточки и акцентный цвет. Это не жёсткая тема: каждый магазин должен иметь свою palette через CSS Variables. 

Интерфейс мобильный в первую очередь, но адаптируется к desktop. Избегать шаблонности, перегруженных градиентов и чрезмерного стеклянного эффекта. Фотографии товаров и ясная иерархия каталога важнее декоративных элементов. 

У каждого сетевого экрана должны быть состояния `loading`, `error`, `empty` и `success`. У всех активных кнопок должно быть реальное действие. Учитывать `prefers-reduced-motion`, клавиатуру, фокус, back navigation Telegram, safe area и реальную высоту нижней панели. 

### Нижняя навигация 

На мобильном экране нижнее меню: 

- Каталог; 
- Корзина; 
- Профиль. 

У корзины счётчик количества. Активный раздел выделен. Панель не закрывает последнюю карточку, поля оформления или кнопку подтверждения; учитывать нижний safe-area inset и добавлять соответствующий padding содержимого. Учитывать Telegram Back при переходе между страницами. 

### Главная 

Показывать логотип/аватарку, название и краткое описание магазина, поиск, категории, выбранные товары/подборки, ссылки на информацию магазина и понятный переход к каталогу. Пустые подборки должны скрываться или иметь корректное состояние, а не показывать пустые декоративные блоки. 

### Каталог 

Категории отображаются в удобном горизонтальном списке либо ином подходящем мобильном компоненте. Поддержать смену выбранной категории, поиск по названию, серверную пагинацию/дозагрузку для больших каталогов и пустое состояние. Архивные категории и неопубликованные товары не показываются публично. 

### Карточка товара 

Показывать фотографию, название, цену, наличие, категорию и доступные варианты. Фото имеют постоянные пропорции внутри списка. Пустая фотография должна иметь нейтральный placeholder. Товар без остатка имеет заметный статус и не может быть заказан. 

### Подробная карточка 

Показывать галерею, описание, цену, доступные варианты вкуса/цвета, количество и действие добавления в корзину. Выбор варианта влияет на цену и остаток, если эти значения отличаются. Нельзя отправить в корзину несуществующую или недоступную комбинацию вариантов. 

### Поиск и состояние каталога 

Не загружать все изображения и весь каталог без необходимости. Search должен быть ограниченным и учитывать магазин. При сетевой ошибке не выдавать кешированные цену/остаток за гарантированно актуальные. До создания заказа всё перепроверяет сервер. 

## 8. Корзина и заказы 

### Корзина 

Реализовать добавление, изменение количества, удаление позиции, очистку, отображение вариантов, цены за единицу, сумм позиций и итоговой суммы. Корзина хранится отдельно для каждого магазина. Допустимо сохранять её локально для UX, но состояние браузера не является источником истины. 

### Checkout 

В первом релизе покупатель создаёт заказ без онлайн-эквайринга. Магазин дальше подтверждает его и согласовывает получение/оплату. Не отмечать заказ оплаченным без подтверждения. 

Перед созданием заказа сервер перепроверяет: 

- магазин опубликован и доступен; 
- каждый товар принадлежит магазину и опубликован; 
- выбран правильный вариант; 
- текущая цена взята из БД; 
- количество — целое положительное допустимое число; 
- остаток достаточен; 
- валюта согласована; 
- идемпотентность соблюдена. 

Нельзя принимать итоговую цену из запроса клиента как правду. 

### Атомарность и конкурентные покупки 

Оформление — одна транзакция PostgreSQL / серверная RPC, обеспечивающая проверку и списание остатков вместе с созданием заказа и его строк. 

Для продаваемых вариантов блокировать нужные строки с корректным порядком блокировки, проверять остаток и атомарно уменьшать его. Два одновременных checkout последних единиц не могут оба завершиться успешно. 

Использовать idempotency key с уникальным ограничением в пределах соответствующего магазина/покупателя. Повтор одинакового запроса возвращает результат исходной операции, а не создаёт новый заказ. 

При отмене резерв/списание должны восстанавливаться не более одного раза. Использовать транзакционное условие статуса и/или журнал складских движений с уникальным ключом операции. Прямые клиентские UPDATE остатков/заказов запрещены; админские операции также проходят валидацию. 

### Статусы и история 

Минимум: `new`, `confirmed`, `ready`, `completed`, `cancelled`; названия в UI можно перевести на русский. Список допустимых переходов определяется явно. Каждый order item хранит snapshot названия, идентификатора варианта, выбранных вкуса/цвета, цены, количества и суммы на момент заказа. Изменение товара не изменяет историю. 

## 9. Telegram Mini App 

Использовать `@tma.js/sdk-react` и официальную документацию Telegram Mini Apps. 

Обеспечить корректное начальное подключение, платформенные возможности, адаптацию к viewport/theme, кнопку Back и поведение при открытии в обычном браузере. Проверять доступность поддерживаемых возможностей до использования. SDK не заменяет безопасность на сервере. 

### Идентификация покупателя 

Для всех операций, которые требуют идентификации в Telegram, сервер проверяет оригинальный `Telegram.WebApp.initData` по официальному алгоритму. Не доверять `initDataUnsafe`, `user.id` из JSON, `username` или localStorage. Проверять подпись и `auth_date` с ограниченным возрастом. При нескольких ботах сервер должен понимать, какой bot identity применяется к запросу; не пробовать проверять данные произвольными токенами. 

Токен Telegram-бота не попадает в браузер. Для одного общего бота конфигурация проще; индивидуальные боты добавлять только при реальной необходимости. Секреты хранить только в серверных секретах/защищённом vault, не в публичной таблице. 

Ссылки должны открывать нужный магазин. Использовать уникальный slug и Telegram deep link/`startapp`, если это соответствует выбранному типу запуска. Например, `/s/<slug>/` — runtime-маршрут приложения, а параметр Telegram передаёт этот slug при старте общего Mini App. Документировать настройку через BotFather и проверять ссылки фактически. 

### Профиль и приватные заказы 

Покупатель не обязан создавать пароль/email-аккаунт. Приватные заказы связаны с подтверждённым Telegram ID и `shop_id`. Клиент получает только свои заказы, и не может прочитать чужие по подстановке `order_id`. Публичный `anon` не имеет SELECT к приватным заказам, контактам, ключам или данным членства. Чтение приватных заказов выполняется функцией, которая подтверждает Telegram `initData` и проверяет принадлежность заказа. 

## 10. Веб-админка 

Веб-админка работает в обычном браузере, адаптивна для компьютера и телефона и не требует входа через Telegram. Авторизация владельца — Supabase Auth email/password. Не включать публичный signup владельцев. Учетные записи создаёт администратор платформы либо контролируемый invite-flow. 

### Обзор 

Показывать настоящие данные магазина: новые/активные/завершённые заказы, товары без остатка, последние заказы. Не показывать моковые метрики в live. Статистика должна фильтроваться по `shop_id` и считать значения из фактических данных. 

### Настройки и тема 

Владелец может менять: 

- название и описание; 
- аватарку/логотип; 
- главную фотографию/обложку, если она используется; 
- основной и акцентный цвета; 
- фон и цвета карточек; 
- допустимые параметры темы; 
- видимость информационных блоков; 
- публичную контактную информацию; 
- порядок и видимость подборок при наличии этой функции. 

Предусмотреть preview и сохранение. CSS Variables обновляются из runtime-конфигурации. Изменения должны публиковаться без новой сборки приложения. 

### Товары 

CRUD товаров: название, описание, категория, цена, изображения, видимость, порядок, варианты и остаток. Для исторических заказов использовать архивирование вместо физического удаления. Товары и варианты принадлежат одному `shop_id`. 

### Варианты 

Упрощённая форма позволяет создать и редактировать вкусы/цвета/другие необходимые характеристики, цену и stock quantity. Разные продаваемые варианты имеют отдельные остатки и уникальные идентификаторы. 

### Категории 

Создание, изменение названия, порядка, изображения, видимости и архивирование. Нельзя допускать поломанных внешних ключей или покупки товара из выключенной категории вопреки правилам публикации. 

### Фотографии 

Выбрать, сжать, загрузить, заменить одно конкретное изображение или удалить его. Замена одного фото не меняет остальные. Пути в Storage организовать по tenant/entity; проверять `shop_id` политиками Storage. Удаление файла выполнять безопасно после проверки использования. 

### Заказы 

Владелец видит только свои заказы и доступные контактные данные. Он может менять статусы в рамках установленной модели. Любые изменения остатка/статуса проверяются сервером. Никаких прямых привилегированных запросов из браузера. 

## 11. Модель данных и миграции 

Реализовать нормализованную схему с внешними ключами, индексами, CHECK и UNIQUE constraints. Все tenant-зависимые таблицы получают `shop_id`. Где нужно для надёжности — добавлять составные уникальные ключи и составные FK, чтобы нельзя было связать товар магазина A с категорией магазина B даже при ошибке приложения. 

Минимальные сущности: 

### `shops` 

- `id`; 
- `slug` с уникальным ограничением; 
- `name`, `description`; 
- `logo_path`, optional `cover_path`; 
- `theme_config` JSONB с валидацией формы на сервере; 
- `currency`; 
- `status` и `mode` (`preview`/`live`); 
- публичные настройки и юридические сведения; 
- `created_at`, `updated_at`. 

### `shop_memberships` 

- `shop_id`; 
- `user_id` из Supabase Auth; 
- роль/набор разрешений; 
- уникальность членства; 
- created_at. 

### `categories` 

- `id`, `shop_id`; 
- `name`, `slug`; 
- `image_path`, optional; 
- `sort_order`; 
- `is_active`, `archived_at` optional. 

### `products` 

- `id`, `shop_id`, `category_id`; 
- `name`, `description`; 
- `base_price_minor` или иной однозначный integer-based формат; 
- `is_published`, `sort_order`; 
- created/updated timestamps. 

Цена хранится целым числом в минимальных единицах валюты либо в другом точно определённом формате без float-ошибок. Валюта фиксируется для магазина/заказа. Не смешивать RUB и другие валюты без явного кода валюты. 

### `product_variants` 

- `id`, `shop_id`, `product_id`; 
- вкус, цвет и другие выбранные характеристики; 
- `sku`, optional; 
- `price_override_minor`, nullable; 
- `stock_quantity`; 
- активность/доступность. 

Цена варианта: `price_override_minor`, если задано, иначе базовая цена товара. Это правило реализовать единообразно на сервере и UI. Остаток варианта всегда целое число, не может быть отрицательным. Для товара без вариантов предусмотреть явный default/sellable variant или чётко определить отдельный путь заказа; предпочтительно единая модель продаваемых stock items. 

### `product_images` 

- `id`, `shop_id`, `product_id`; 
- storage path; 
- sort_order; 
- is_primary; 
- alt_text; 
- created_at. 

### `orders` 

- `id`, `shop_id`; 
- проверенная идентичность покупателя Telegram; 
- номер заказа; 
- статус; 
- валюта и итоговая сумма; 
- `idempotency_key`; 
- состояние резервирования/обработки остатков; 
- created/updated timestamps. 

### `order_items` 

- `id`, `shop_id`, `order_id`; 
- product/variant reference, если нужен для аудита; 
- snapshot названия, варианта, вкуса/цвета; 
- единичная цена на момент заказа; 
- количество; 
- snapshot итога позиции. 

### `inventory_movements` или эквивалент 

Добавить при необходимости для аудита изменения складских остатков и гарантии однократного восстановления при отмене. Если используется, журнал должен иметь уникальные ключи операций для защиты от повторов. 

Схема не должна хранить весь каталог в одной JSON-колонке. JSONB использовать для конфигурации темы/настроек, а товары, категории, варианты, изображения и заказы хранить в реляционных таблицах. 

## 12. RLS, GRANT и границы доверия 

RLS включить на всех таблицах, доступных через API. Права `GRANT` должны быть столь же строгими, как политики. Публичный пользователь может читать только опубликованный каталог/публичную конфигурацию. `anon` не должен читать приватные заказы, контакты, membership, idempotency keys или служебные записи. 

Владелец авторизуется через Supabase Auth. Доступ к магазину подтверждается серверной проверкой `shop_memberships`; нельзя доверять роли, переданной frontend. Администратор платформы получает отдельные контролируемые полномочия. 

Storage policies обязаны ограничивать приватные операции тем же tenant. Публичное чтение файлов допустимо только для изображений, предназначенных для опубликованной витрины. 

`service_role` и Telegram Bot Token остаются серверными. Если Edge Function использует service role, она вручную подтверждает caller identity и разрешённую операцию. Не использовать широкую политику `USING (true)`/`WITH CHECK (true)` для изменения данных. 

Создать тесты как разрешённых, так и запрещённых операций. Одного успешного теста владельца недостаточно: проверить, что владелец A не получает данные B. 

## 13. Конвейер создания tenant 

Создать реальные команды в `package.json` и скрипты в `scripts/`: 

- `pnpm tenant:new --slug <slug>` — создаёт папку и шаблон конфига, проверяет slug и не перезаписывает существующий tenant без явного флага; 
- `pnpm tenant:validate --slug <slug>` — валидирует схему Zod, slug, цвета, обязательные поля, пути и изображения; 
- `pnpm tenant:seed --slug <slug>` — идемпотентно импортирует начальные данные в Supabase и не перезаписывает изменённые владельцем значения; 
- `pnpm tenant:publish --slug <slug>` — переводит магазин в live только после необходимых проверок и явного действия; 
- `pnpm tenant:verify --slug <slug>` — проверяет конфигурацию, доступность публичного каталога, права владельца, изображения и готовность ссылок. 

Команды должны быть реализованы, иметь exit code, понятные сообщения и документацию. Не оставлять их только в README. При повторном запуске `new`/`seed` не создавать дубликаты. Публикация должна проверять preview/live, обязательную юридическую конфигурацию и наличие минимально необходимых данных. 

Конфиг — вход для tenant-пайплайна. После начального seed runtime-настройки читаются из Supabase; изменения в админке не требуют нового deploy. Не генерировать отдельные JS/CSS-бандлы для каждого магазина. 

## 14. Демо-данные 

Создать минимум два явно отличающихся demo tenants с разными названиями, палитрами, категориями и товарами. Например, один в тёмном премиальном стиле, второй — в светлом минималистичном. Имена и товары демонстрационных бизнесов должны существовать в `tenants/` и seed, а не быть разбросанными по `src/`. 

Demo режим должен быть помечен и не должен создавать настоящие заказы/внешние уведомления или смешиваться с live-магазинами. Создание и удаление тестовых данных должно быть воспроизводимым и безопасным. 


## 15. Приёмочные проверки 

### Unit 

- Zod-конфигурация tenant; 
- theme tokens и применённая палитра; 
- формула цены с `price_override_minor`; 
- валидация вариантов; 
- расчёт суммы заказа; 
- статусы заказа; 
- ключи кэша и разделение tenant; 
- проверки конфигурации/seed. 

### SQL/integration 

- публичный SELECT видит только опубликованные поля/товары; 
- anon не читает приватные заказы и memberships; 
- owner A читает и меняет только tenant A; 
- owner A не может вставить товар в категорию tenant B; 
- доступ к чужому Storage path запрещён; 
- две конкурентные покупки последней единицы не проходят одновременно; 
- повтор idempotency key возвращает существующий заказ; 
- отмена возвращает запас не более одного раза; 
- изменение цены не меняет snapshot в старом заказе; 
- чужой Telegram ID не читает заказ; 
- неверный/просроченный initData отклоняется. 

### Playwright flow 

Выполнить end-to-end сценарий: 

1. Открыть demo tenant. 
2. Перейти в категорию. 
3. Открыть товар. 
4. Выбрать вкус/цвет. 
5. Добавить товар в корзину. 
6. Создать тестовый заказ в тестовом контуре/tenant. 
7. Подтвердить, что заказ и snapshot цены сохранены. 
8. Зайти в админку владельцем этого tenant. 
9. Убедиться, что новый заказ отображается. 
10. Изменить остаток, цену или доступность варианта. 
11. Проверить обновление каталога. 
12. Проверить, что владелец второго tenant не видит этот заказ и не меняет товар. 

Если Telegram-подпись или реальные credentials недоступны в CI, разделить unit/integration проверки на полностью тестируемые части и явно записать, какие реальные интеграционные проверки остались невыполненными. Не подменять результат моковым ответом и не называть mock реальной Telegram-интеграцией.

## 18. Последовательность реализации 

Выполнять этапы последовательно, после каждого выполнять соответствующие проверки и корректировать ошибки. 

### Этап 1. Аудит 

Изучить repo, `AGENTS.md`, skills, design system, MCP, существующие credentials и Git status. Не терять незакоммиченные изменения. 

### Этап 2. Каркас и UI foundations 

Настроить Vite, React, TypeScript strict, pnpm, React Router, Tailwind/shadcn/Astryx. Создать общие компоненты, основу theme tokens, responsive shell, нижнюю навигацию и главные состояния. 

### Этап 3. Supabase схема 

Создать миграции, сущности, индексы, ограничения, GRANT, RLS и Storage policies. Применить их в выбранном проекте при доступных правах. Написать тесты tenant isolation. 

### Этап 4. Tenant runtime/config pipeline 

Создать загрузку настроек из Supabase, динамические CSS tokens и команды `tenant:new`, `tenant:validate`, `tenant:seed`, `tenant:publish`, `tenant:verify`. Создать два demo tenants и проверить отсутствие tenant-specific названий в `src/`. 

### Этап 5. Витрина 

Реализовать каталог, категории, поиск, карточки товаров, варианты вкуса/цвета, галерею, наличие, загрузку изображений и состояния сети. 

### Этап 6. Корзина и оформление 

Реализовать корректное хранение корзины по tenant, серверную проверку цен/остатков, атомарное создание заказа, idempotency и отмену. 

### Этап 7. Telegram и профиль 

Реализовать SDK, запуск по ссылке, проверку initData, профиль и доступ к собственным заказам. Не подменять внешнюю интеграцию моками без явной маркировки. 

### Этап 8. Админка 

Реализовать Supabase Auth, проверку членства, редактирование темы/названия/логотипа, CRUD товаров и категорий, вариантов/вкусов/цветов, остатков, фотографий и заказов. 

### Этап 9. Проверки и hardening 

Запустить lint, `tsc`, unit, SQL/integration и Playwright. Проверить конкурентный checkout, повторный запрос, RLS и переключение между tenants. Исправить ошибки. 

### Этап 10. Деплой и документация 

Развернуть через Vercel MCP/CLI . Проверить опубликованную ссылку, маршруты и работу Supabase. Дополнить SETUP, README, CLONE-IN-6-MINUTES и ACCEPTANCE фактическими результатами. 

## 19. Критерии завершения 

Продукт готов только если подтверждено, что: 

1. Работает публичный каталог. 
2. Mini App открывается в Telegram. 
3. Нижняя навигация ведёт в каталог, корзину и профиль. 
4. Работают поиск и категории. 
5. Карточки товаров загружаются из Supabase. 
6. Можно выбрать вкус/цвет и увидеть соответствующие цену/остаток. 
7. Корзина корректно считает позиции и сумму. 
8. Сервер перепроверяет цену и остаток. 
9. Заказ создаётся атомарно, а повторный запрос не создаёт дубликат. 
10. Остаток не уходит ниже нуля при конкурентном заказе. 
11. Покупатель видит только собственные заказы. 
12. Владелец входит через защищённую админку. 
13. Владелец может менять название, логотип, палитру, категории, товары, фотографии, вкусы, цвета, цены и остатки. 
14. Изменения появляются без нового frontend deploy. 
15. Разные tenants изолированы на уровне БД, Storage и серверных функций. 
16. Создание следующего tenant не требует изменения исходников приложения. 
17. Все tenant-команды реально работают и описаны. 
18. Тесты выполняются; пропущенные внешние проверки перечислены. 
19. Публичная ссылка проверена после deploy, если credentials и допустимый тариф доступны.
